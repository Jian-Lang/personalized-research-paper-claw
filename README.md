# 🧭 Personalized Research Paper Claw

A local-first research and learning system in which a **Research Agent** proactively advances paper discovery, filtering, reading, and organization, while **Human-in-the-loop** controls preserve your **personal preferences and critical judgment**.

Continuously receive top-conference papers that match your research trajectory, then preserve them as long-term notes organized around your own knowledge structure.

## 💡 Why Personalized Research Paper Claw?

> **From paper overload to a research memory that keeps growing.**
>
> Imagine it is 1 a.m. An experiment has just finished, dozens of paper tabs are still open, and a new conference acceptance list appears in your group chat. Hundreds or thousands of papers form an endless queue. You know only a handful are truly relevant, but the list does not know what you care about and cannot skip work that looks related while being irrelevant in practice.
>
> You eventually choose a few papers and promise to read them tomorrow. Days later, the PDFs are buried in Downloads, summaries remain in an old conversation, and scattered judgments live in temporary Markdown files. When it is time to write related work, you only remember that you “read something like this,” not what it solved, how it related to prior work, or why it mattered.

Personalized Research Paper Claw starts from these two moments:

- 📬 **Daily Conf Paper Delivery** remembers your topics, keywords, exclusions, and thresholds. It selects genuinely relevant work from continuously updated conference acceptance lists and delivers summaries, match reasons, and reading priorities.
- 📝 **Research Paper Noter** takes over the papers you choose to read deeply. It creates detailed notes and, in Domain mode, organizes them into a browsable Research Gallery with one-click HTML export for flexible sharing. It also explains how each paper inherits from, contrasts with, or complements related work.

One component makes worthwhile papers appear on time; the other prevents what you have read from disappearing. “Personalized” does not mean silently guessing your interests: you explicitly configure recommendation criteria and category structures. The long-term knowledge source consists of ordinary Markdown files in a global notes directory that you own, with HTML generated only when you explicitly request a shareable export. We strongly recommend Obsidian for reading and maintaining these assets.

**Scope:** Personalized Research Paper Claw does not write papers or run experiments automatically. It focuses on personalized paper discovery, reading, and knowledge organization.

## 📬 Daily Conf Paper Delivery

Daily Conf Paper Delivery puts work worth reading in front of you. It scans the bundled, locally maintained AI conference lists, such as NeurIPS, ICML, ICLR, and CVPR, without fetching conference data from the network at runtime. It scores title + abstract using your preferences. Every conference maintains its own cursor, so each run continues from the last scanned position and creates a new daily recommendation page.

The repository currently includes **ICML 2026, ICLR 2026, CVPR 2026, and ACL 2026**. Curated acceptance-list updates will continue to be added for important new conferences.

You can also add conferences or journals from other fields by following the [custom source guide below](#custom-conference-journal-lists).

The default pipeline has two stages:

1. **Filter**: score papers using topics, keywords, exclusions, and the configured threshold.
2. **Summarize and review**: use only abstracts and existing structured metadata to assign reading priority and topic, create a summary note for each paper, and collect the day’s recommendations in one page.

The recommendation page begins with a sharp daily overview and a Must read / Worth reading / Skip triage table. Each summary note contains authors, affiliations, source and paper links, a teaser figure when available, a one-sentence summary, the original English abstract and a Chinese translation, background, motivation, core method, evaluation, takeaways, and a concise critique.

<a id="scoring"></a>

### 🎯 Recommendation Logic

Daily Conf Paper Delivery has two positive preference inputs:

- `topics`: broader research areas, also used to organize the recommendation page.
- `keywords`: specific methods, tasks, and expressions that require precise attention.

#### 🧮 Scoring

| Match location | Score | Behavior |
| --- | ---: | --- |
| One topic fully matches the title or abstract | `+1` | Each topic is counted once per paper |
| One keyword fully matches the title | `+3` | Its abstract match is not counted again |
| One keyword matches only the abstract | `+1` | Counted only when the title did not match |
| One exclusion keyword matches the title or abstract | `-100` | The paper is excluded |

The default `min_score` is `2`. A paper matching only one topic is therefore not recommended; it must also match a keyword or receive support from another topic.

Matching normalizes case and punctuation and respects complete word or phrase boundaries. Case- or hyphen-equivalent duplicates in the configuration count only once. Every candidate includes a `score_breakdown` so you can inspect why it was selected.

Each conference contributes at most `daily_take` papers per day. Starting from its current cursor, the pipeline scans at most `scan_limit` entries, which defaults to 1000. It stops when the quota is filled, the scan limit is reached, or the list ends, so the actual recommendation count may be smaller. `shuffle` controls stable mixing of a conference list and does not change relevance scores.

For manual setup, prepare compatible JSONL and place it at:

```text
daily-conf-paper-delivery/data/paperlist/<CONF>/<conf>_<year>.jsonl
```

For example:

```text
daily-conf-paper-delivery/data/paperlist/NEURIPS/neurips_2026.jsonl
```

Each line represents one paper. `title` and `abstract` are required; `author`, `site`, `pdf`, and `status` are optional. Then add the source to `daily_papers.conferences`:

```json
{ "name": "NEURIPS", "year": 2026, "daily_take": 5 }
```

If you already maintain a local paperlist with the same directory layout, import the configured conference files with:

```bash
cd daily-conf-paper-delivery
python3 scripts/sync_paperlist.py --source-dir /path/to/local/paperlist
```

This script reads only the local directory you specify and does not depend on an external paper-list repository.

## 📝 Research Paper Noter

Research Paper Noter preserves papers you have decided to read. Inputs can be paper titles, arXiv URLs, DOIs, local PDFs, Zotero items, or title lists.

> **🖼️ Highlight — Domain Research Gallery**: this is more than placing Markdown files in folders. It organizes papers under a domain by category and year into a research gallery designed to keep growing. Every newly added work includes a teaser figure, key information, a detailed-note entry point, and its inheritance, contrast, and complementarity relationships with work in the same batch or field. In addition to the Markdown Gallery that remains the long-term knowledge source, one command can export a carefully typeset, responsive **HTML reading page**. Year navigation, paper cards, figures, abstracts, core methods, evaluations, and paper relationships remain intact, so the page can be opened, hosted, and shared without Obsidian.

It supports two long-term organization modes:

| Mode | Best for | Output |
| --- | --- | --- |
| **Personalized** | Maintaining papers that you deliberately selected and read | Detailed notes + `PersonalizedPaperContent.md` |
| **Domain Research Gallery** | Maintaining browsable related work around a field and its subcategories | Detailed single-paper notes + Domain Research Gallery overview pages + on-demand Gallery HTML |

Personalized mode appends and deduplicates papers by topic. Domain Research Gallery mode separates detailed notes from category Galleries. Each category page sorts papers by year and publication date and shows a teaser figure, one-sentence summary, bilingual abstract, method, evaluation, takeaways, and relationships to other work. The domain index connects all categories while preserving handwritten content in content pages.

You define the `domain / category` hierarchy for your own paper knowledge base. It is separate from the `topics` used by Daily Conf Paper Delivery for recommendation scoring and grouping.

## 📦 Installation

### 🧰 Requirements

- [Codex CLI](https://github.com/openai/codex)
- Python 3.8+
- [Obsidian](https://obsidian.md/), strongly recommended but not required. Markdown remains the long-term source of truth; HTML can be exported for sharing.
- [Zotero](https://www.zotero.org/), optional
- Poppler, optional but recommended for extracting figures from PDFs

Install Poppler on macOS with Homebrew:

```bash
brew install poppler
```

### 📥 Clone the Repository

```bash
git clone https://github.com/Jian-Lang/personalized-research-paper-claw.git
cd personalized-research-paper-claw
```

Cloning the repository does not start a paper workflow or register a background task. After configuration and Skill installation, a run still requires an explicit request such as “Recommend today’s papers.” Automatic recommendations begin only after you deliberately install a scheduled task.

### 🔗 Install the Skills

Symbolic links are recommended. They let Skills read the configuration, scripts, and conference data from the current checkout, so repository updates require no repeated copying. Natural-language schedule management also uses these links to locate the scheduler.

If a Skill with the same name already exists at the destination, back it up or move it before running:

```bash
SKILLS_DIR="${CODEX_HOME:-$HOME/.codex}/skills"
mkdir -p "$SKILLS_DIR"

ln -s "$PWD/daily-conf-paper-delivery/skills/_shared" "$SKILLS_DIR/_shared"
ln -s "$PWD/daily-conf-paper-delivery/skills/daily-papers" "$SKILLS_DIR/daily-papers"

ln -s "$PWD/daily-conf-paper-delivery/skills/daily-papers-notes" "$SKILLS_DIR/daily-papers-notes"
ln -s "$PWD/research-paper-noter/skills/manual-papers" "$SKILLS_DIR/manual-papers"
ln -s "$PWD/research-paper-noter/skills/domain-papers" "$SKILLS_DIR/domain-papers"
```

## 🚀 Usage

### 📁 Prerequisite: Configure the Global Markdown Root

All recommendation pages, detailed notes, and domain Galleries remain local as ordinary Markdown files. Explicit HTML exports are stored inside their corresponding domains. You configure one globally writable directory; Daily, Personalized, and Domain subdirectories are created naturally the first time each Skill runs. No Markdown files need to exist beforehand.

Create the root configuration:

```bash
cp config/user-config.example.json config/user-config.local.json
```

Edit `config/user-config.local.json`:

```json
{
  "paths": {
    "markdown_root": "~/ResearchNotes"
  }
}
```

This root configuration has one responsibility: choosing where all Markdown is stored. Daily and Noter preferences and automation switches remain in their own configurations.

`markdown_root` may be an existing Obsidian vault or an ordinary folder. If it does not exist, the first run creates it. Obsidian does not need to be open, and Daily, Personalized, or Domain directories do not need to be prepared manually.

Directories appear on demand:

```text
{markdown_root}/
├── DailyPapers/                    # Created on the first daily recommendation
├── PersonalizedPaper/             # Created on the first manual paper workflow
└── DomainPapers/                   # Created on the first Domain paper workflow
```

> We strongly recommend Obsidian for reading this Markdown. It is not a runtime dependency and does not require Obsidian Sync. Instructions are provided later in this section.

### ⚡ Quick Start: Generate Your First Daily Recommendation

#### ⚙️ 1. Configure Daily Preferences

The easiest option is to tell Codex:

```text
Initialize my Daily recommendation configuration.
My research areas are Recommendation Systems and LLM-based Recommendation.
Prioritize personalized recommendation assistants and conversational recommendation.
Exclude medical and robotic work.
```

The `daily-papers` Skill creates the local configuration from the template, preserves default conferences and runtime settings, and writes your areas, keywords, and exclusions. It configures only; it does not start a recommendation run.

You can also create the file manually:

```bash
cp daily-conf-paper-delivery/skills/_shared/user-config.example.json \
  daily-conf-paper-delivery/skills/_shared/user-config.local.json
```

Before the first run, verify at least these fields:

| Setting | Purpose |
| --- | --- |
| `daily_papers.conferences` | Conferences and years to use |
| `daily_papers.conferences[].daily_take` | Per-conference daily maximum; defaults to `5` |
| `daily_papers.scan_limit` | Maximum entries scanned after the current cursor per conference and day; defaults to `1000` |
| `daily_papers.topics` | Research areas and recommendation-page categories |
| `daily_papers.keywords` | Specific method names, task names, and synonymous expressions |
| `daily_papers.exclude_keywords` | Areas that must not enter recommendations |
| `daily_papers.min_score` | Recommendation threshold; defaults to `2` |

Minimal example:

```json
{
  "daily_papers": {
    "conferences": [
      { "name": "ICML", "year": 2026, "daily_take": 5 },
      { "name": "ICLR", "year": 2026, "daily_take": 5 },
      { "name": "CVPR", "year": 2026, "daily_take": 5 },
      { "name": "ACL", "year": 2026, "daily_take": 5, "shuffle": true }
    ],
    "scan_limit": 1000,
    "topics": [
      "MLLM Personalization",
      "Test-Time Adaptation"
    ],
    "keywords": [
      "personalized mllm",
      "multimodal memory",
      "test-time adaptation"
    ],
    "exclude_keywords": [
      "medical",
      "robotic"
    ],
    "min_score": 2
  }
}
```

Both the global configuration and the local Daily configuration are ignored by git.

#### ▶️ 2. Run the Recommendation

In a new Codex session, say:

```text
Recommend today's papers.
```

The default pipeline filters and reviews the papers, then writes:

```text
{markdown_root}/DailyPapers/mocs/DailyPaperContent-YYYY-MM-DD.md
```

#### ☀️ 3. Enable Automatic Daily Recommendations

After verifying the first recommendation, tell Codex:

```text
Recommend papers every day at 8:00 a.m.
```

The time is stored in Daily’s `automation.daily_run_time` using 24-hour `HH:MM` format:

```json
{
  "automation": {
    "daily_run_time": "08:00"
  }
}
```

To change the time, say:

```text
Move the daily recommendation to 09:30.
```

The `daily-papers` Skill updates `automation.daily_run_time`, reloads the local scheduled task, and verifies its status. This step is optional. Enabling or changing the schedule does not run an extra recommendation immediately; automatic execution begins at the next configured time.

### 📬 Using Daily Conf Paper Delivery

#### 💬 Common Requests

| What you tell Codex | Result scope |
| --- | --- |
| `Recommend today's papers` | At most `daily_take` papers per conference |
| `Recommend papers from the past 3 days` | At most `daily_take × 3` papers per conference |
| `Recommend papers from the past week` | At most `daily_take × 7` papers per conference |
| `Recommend papers every day at 8:00 a.m.` | Enable or update the daily schedule |
| `Show the daily recommendation schedule` | Show whether it is enabled and its current time |
| `Disable daily paper recommendations` | Remove the local scheduled task |

Repeated runs on the same day reuse that day’s result and do not advance cursors. Each conference has its own cursor and `daily_take`, so configuration directly determines recommendation counts and proportions.

“Past N days” means collecting N daily quotas from papers not yet recommended; it does not filter conference acceptance lists by paper publication date.

#### 🧪 Optional Single-Stage Requests

These requests exist, but they have different prerequisites:

| Request | Prerequisite | Effect |
| --- | --- | --- |
| `Run paper fetching` | Configuration and local conference lists are ready | Score and deduplicate papers, then create `/tmp/daily_papers_enriched.json` |
| `Run paper review` | Fetching completed successfully | Read the enriched result and create the day’s recommendation page |
| `Run paper notes` | The enriched result and daily page both exist | Create detailed notes for the three highest-scoring papers and backfill links |
| `Refresh the paper index` | The Obsidian notes directory is writable | Regenerate paper index / MOC pages manually |

`Run paper notes` is an optional third stage. It is not part of the default “Recommend today’s papers” flow and cannot run independently without the first two stages’ artifacts.

#### ⏰ Scheduling from Natural Language

There is no need to edit time fields or memorize scripts. Tell Codex:

```text
Recommend papers every day at 8:00 a.m.
Move the daily recommendation to 09:30.
Show the daily recommendation schedule.
Disable daily paper recommendations.
```

On macOS, the `daily-papers` Skill updates the Daily configuration, installs or removes a launchd task, and verifies the result. Enabling the schedule does not immediately run a catch-up job. Cloning the repository, installing Skills, or merely filling in `daily_run_time` never enables a background task by itself.

For troubleshooting or direct operation without Codex:

```bash
cd daily-conf-paper-delivery
./bin/configure-schedule.sh --time 08:00
./bin/configure-schedule.sh --status
./bin/configure-schedule.sh --remove
```

### 📝 Using Research Paper Noter

Research Paper Noter reuses the root `config/user-config.local.json`; it does not maintain another notes-root setting.

| Directory | Purpose |
| --- | --- |
| `{markdown_root}/PersonalizedPaper` | Deliberately selected reading and cumulative summaries |
| `{markdown_root}/DomainPapers` | Research Galleries organized by domain/category |

Zotero is optional. When needed, copy `research-paper-noter/skills/_shared/user-config.example.json` and configure the database, attachment paths, and Noter-specific index and git behavior.

#### 📌 Personalized: Maintain Your Deliberate Reading List

Tell Codex:

```text
Add this to my personalized reading notes: Retrieval-Augmented Dynamic Prompt Tuning for Incomplete Multimodal Learning
```

For a batch, continue listing titles, arXiv URLs, or DOIs. The workflow creates or reuses each detailed note and appends it to:

```text
{markdown_root}/PersonalizedPaper/
├── mocs/PersonalizedPaperContent.md
└── papers/
```

Or use the shell entry point:

```bash
cd research-paper-noter
./bin/paper-read.sh "Paper title or arXiv URL"
```

To read a single paper without maintaining Personalized or Domain summaries, simply say:

```text
Read this paper: <arXiv URL, title, or local PDF>
```

#### 🖼️ Domain Research Gallery: Turn Related Work into a Browsable Field Map

Provide the domain, category, and paper explicitly:

```text
Organize a domain paper:
Domain: MLLM Personalization
Category: Personalized Understanding / Long-Context Personalization
Paper: TAMEing Long Contexts in Personalization: Towards Training-Free and State-Aware MLLM Personalized Assistant
```

Both `Domain` and `Category` are required when adding a paper. Under the `MLLM Personalization` domain, `Category` may contain one level, such as `Personalized Understanding`, or multiple levels separated by `/` or `>`, such as `Personalized Understanding / Long-Context Personalization`.

Shell entry point:

```bash
cd research-paper-noter
./bin/domain-paper-add.sh \
  "MLLM Personalization" \
  "Personalized Understanding / Long-Context Personalization" \
  "TAMEing Long Contexts in Personalization: Towards Training-Free and State-Aware MLLM Personalized Assistant"
```

Detailed notes and Galleries are kept strictly separate:

```text
{markdown_root}/DomainPapers/{domain}/
├── paper/                         # Complete note for each paper
├── content/
│   ├── _index.md                  # Domain Gallery entry point
│   └── {category_path}.md         # Browsable category Gallery
└── html/                          # Created only after an explicit export
    ├── index.html                 # Share page for the whole domain
    └── {category_slug}.html       # Share page for one subfield
```

Whenever a paper is added, Noter updates its category Gallery. Entries are organized by year and publication date and show the teaser figure, core method, evaluation, and practical takeaways. “Relationships to other work” explains what the paper inherits, contrasts with, or complements. Obsidian wikilinks connect Gallery entries to detailed notes, supporting both horizontal browsing and deep reading.

> **`Note`**: in a multi-level category, earlier levels become directories and the deepest level becomes the actual Gallery file.
>
> - Two levels: `LLM-based Recommendation / Conversational Recommendation` → `content/LLM-based Recommendation/Conversational Recommendation.md`
> - Three levels: `LLM-based Recommendation / Conversational Recommendation / User Profiles` → `content/LLM-based Recommendation/Conversational Recommendation/User Profiles.md`
>
> Parent levels do not automatically receive additional aggregate Galleries.

#### ♻️ Rebuild Category Galleries After Bulk Changes

After bulk changes to a domain’s paper set, categories, or base metadata, explicitly rebuild either every category Gallery in that domain or one subfield:

```text
Rebuild all category Galleries under the Recommendation Systems domain.
Rebuild the LLM-based Recommendation Gallery under the Recommendation Systems domain.
```

The corresponding scripts are:

```bash
cd research-paper-noter
./bin/domain-paper-gallery-rebuild.sh "Recommendation Systems"
./bin/domain-paper-gallery-rebuild.sh \
  "Recommendation Systems" \
  "LLM-based Recommendation"
```

Adding a paper for the first time still requires `domain + category`, because the system must know which inner Gallery receives it. Bulk rebuild requires only the domain because existing notes already record their categories. Rebuilding uses detailed notes to confirm paper membership, classification, and base metadata while preserving curated Gallery summaries and relationships from sidecars. It refreshes category Galleries and the domain index, but does not create an outer aggregate Gallery: `content/_index.md` remains a navigation entry point. Rebuilding does not regenerate paper notes, export HTML, commit, or push, and normal paper addition never triggers a bulk rebuild automatically.

#### 🌐 Export a Share-Ready Gallery HTML Page

Once a Domain Research Gallery is mature, export it as a standalone static HTML reading page. The export preserves figures, years and venues, abstracts, core methods, evaluations, takeaways, paper relationships, clear navigation, and responsive typography. It requires no Obsidian and can be opened directly or hosted on a personal or static website.

Export an entire domain, merging all categories and subcategories into one page while labeling every paper with its subfield:

```text
Export the Recommendation Systems domain as HTML.
```

To share one subfield, include its category path. Multi-level paths continue to use `/`:

```text
Export the LLM-based Recommendation subfield of Recommendation Systems as HTML.
```

Shell entry points:

```bash
cd research-paper-noter
./bin/domain-paper-gallery-html.sh "Recommendation Systems"
./bin/domain-paper-gallery-html.sh \
  "Recommendation Systems" \
  "LLM-based Recommendation"
```

HTML is written to `{markdown_root}/DomainPapers/{domain}/html/` by default. Export is fully on demand: adding domain papers does not automatically generate HTML and does not modify existing notes, content Galleries, or indexes.

### 🔮 Strongly Recommended: Read the Notes in Obsidian

Obsidian treats a local folder as a vault; no Markdown import or conversion is required:

1. Install and open [Obsidian](https://obsidian.md/).
2. Select **Open folder as vault**.
3. Choose the configured `markdown_root`, for example `~/ResearchNotes`.
4. Obsidian displays `DailyPapers`, `PersonalizedPaper`, and `DomainPapers`, and recognizes generated `[[wikilinks]]`, images, and index pages.

Obsidian creates its own `.obsidian` configuration directory; this project does not create or modify it. Obsidian Sync is optional. Future Markdown created by a Skill appears directly in the same vault.

## ⚠️ Project Boundaries

- Daily recommendations use title + abstract from conference lists; they are not full-paper reviews.
- Detailed notes read more of the paper, but AI-generated facts, formula explanations, and evaluations still require human verification.
- Zotero is an optional input source; Daily recommendations do not depend on it.
- Obsidian is strongly recommended for browsing and wikilinks. Standard Markdown remains the long-term knowledge source; HTML is generated only after an explicit sharing request.
- Git commit, push, and Obsidian synchronization are disabled by default. Codex reads only the notes required to complete the current task.
